# AXI-LITE2SPI 项目梳理

## 项目定位

AXI-LITE2SPI 验证的是一个 memory-mapped 配置接口到串行外设接口的协议桥。CPU 侧通过 AXI4-Lite 写寄存器，把 SPI mode、SCK 分频、字长、片选时序和 MOSI 数据交给 DUT。`WSTRB` 属于 AXI 写数据通道上的字节使能信号，用来决定 `WDATA` 的哪些 byte lane 写入目标寄存器。

DUT 内部寄存器保存这些配置，SPI master 在 `START` 写 1 后按照寄存器值发出一帧 SPI 传输。

验证环境要完成两件事。第一，AXI master agent 要产生真实 AXI-Lite 读写，让 DUT 的寄存器和状态路径被实际访问。第二，monitor、reference model、scoreboard 要把总线上已经发生的事实转换成可比较的 transaction，判断 DUT 的 SPI 输出是否符合 AXI 输入事务所要求的行为。

当前项目的检查主线是：

```text
AXI 写配置 / 写 MOSI_DATA / 写 START
  -> DUT 保存配置并发起 SPI frame
  -> AXI monitor 采样 AXI 通道事件
  -> reference model 根据 AXI 事务生成 expected SPI item
  -> SPI monitor 采样真实 MOSI frame
  -> scoreboard 比较 expected SPI item 和 actual SPI item
```

RM 负责从输入事务推导期望输出，scoreboard 负责比较，coverage 负责统计测试空间。

## 静态结构

UVM component 树的核心结构如下。

```text
uvm_test_top : <current test>
├── env_cfg : environment_config
│   ├── axi_cfg : axi_config
│   └── spi_cfg : spi_config
└── env : tb_environment
    ├── axi_agt : axi_agent
    │   ├── axi_sqr : axi_sequencer
    │   ├── axi_drv : axi_driver
    │   └── axi_mtr : axi_monitor
    ├── spi_mtr : spi_monitor
    ├── rm : spi_ref_model
    │   ├── axi_fifo
    │   └── expected_spi_item
    ├── scb : tb_scoreboard
    │   ├── expected_spi_fifo
    │   └── actual_spi_fifo
    └── cov : tb_coverage
        ├── axi_export
        └── spi_export
```

`env / agent / driver / monitor / rm / scoreboard / coverage` 是 `uvm_component`，会出现在 topology 里。`axi_seq_item`、`spi_seq_item`、`axi_spi_cfg_seq` 这类对象是 `uvm_object`，由 sequence 或 monitor 临时创建，用来表示一笔事务或一帧数据。

## tb_top 的硬件世界

`tb_top.sv` 是 SystemVerilog module，负责建立真实硬件连接。它生成 `s00_axi_aclk` 和 `s00_axi_aresetn`，实例化 `axi_interface` 和 `spi_interface`，再把 interface 信号接到 DUT 端口。

`tb_top` 还实例化两个检查相关对象：

| 对象 | 作用 |
|---|---|
| `spi_sva_checker` | 检查 SPI 复位 idle |
| `axi_sva_checker` | 检查 AXI reset idle、payload stable until ready、读写响应返回等周期级性质 |
| `spi_miso_slave_model` | 给 MISO readback 类测试提供从设备返回数据 |

UVM class 不能直接实例化硬件 interface。`tb_top` 用 `uvm_config_db` 把真实 interface 句柄交给 UVM 世界：

```systemverilog
uvm_config_db#(virtual axi_interface)::set(null, "uvm_test_top", "axi_vif", axi_vif);
uvm_config_db#(virtual spi_interface)::set(null, "uvm_test_top", "spi_vif", spi_vif);
run_test();
```

## build_phase 的创建和配置

`build_phase` 从上到下建立环境。`test_base` 创建 `env_cfg`、`axi_cfg`、`spi_cfg`，从 `config_db` 取回 `axi_vif` 和 `spi_vif`，再把配置对象交给 `env`。

```text
tb_top
  set axi_vif / spi_vif
  run_test()

test_base
  create env_cfg / axi_cfg / spi_cfg
  get axi_vif / spi_vif
  env_cfg.axi_cfg.vif = axi_vif
  env_cfg.spi_cfg.vif = spi_vif
  set environment_config to env
  create env

tb_environment
  get environment_config
  set axi_config to axi_agt / spi_mtr / rm / scb
  set spi_config to spi_mtr
  create axi_agt / spi_mtr / rm / scb / cov
```

当前 `tb_environment` 中，`axi_config` 被分发给 `rm` 和 `scb`，主要用于 reset 监听。reset 来时，RM 清 AXI 暂存队列和 shadow 配置，SCB 清 expected/actual FIFO。

## connect_phase 的数据线

`connect_phase` 只建立 TLM 通信路径。真正的数据传输发生在 run phase 中。

当前连接关系是：

```systemverilog
axi_agt.axi_mtr_port.connect(rm.axi_fifo.analysis_export);
rm.expected_spi_item.connect(scb.expected_spi_fifo.analysis_export);
spi_mtr.spi_mtr_port.connect(scb.actual_spi_fifo.analysis_export);

axi_agt.axi_mtr_port.connect(cov.axi_export);
spi_mtr.spi_mtr_port.connect(cov.spi_export);
```

对应的数据流：

```text
AXI monitor -> RM -> scoreboard expected FIFO
SPI monitor -> scoreboard actual FIFO
AXI monitor -> coverage
SPI monitor -> coverage
```

`uvm_analysis_port` 是单向广播。发送端调用 `write(item)` 后，连接到这个 port 的接收端都会得到 transaction。`uvm_tlm_analysis_fifo` 可以把 analysis 的非阻塞 `write()` 转成 run phase 里可阻塞的 `get()`，所以 RM 和 SCB 可以用后台线程按顺序处理数据。

## 激励执行线

激励从 test 的 sequence 开始，经过 sequencer 和 driver，最后变成 interface 上的 AXI 信号。

```text
test
  -> sequence
  -> sequencer
  -> driver
  -> virtual interface
  -> DUT AXI slave
```

sequence 负责描述“要做哪笔事务”。driver 负责把事务翻译成协议时序。

```systemverilog
seq = axi_spi_cfg_seq::type_id::create("seq");
seq.word_len_i  = 2'b01;
seq.mosi_data_i = 32'h1234;
seq.start(env.axi_agt.axi_sqr);
```

sequence 内部通过 `start_item()` / `finish_item()` 交付 item：

```systemverilog
start_item(item);
item.write = 1'b1;
item.addr  = addr;
item.wdata = data;
item.wstrb = 4'hF;
finish_item(item);
```

driver 用 `get_next_item()` 拉取 sequence item，并把一笔读写请求拆成 AXI 通道级工作。写请求拆成 AW、W、B 三个通道任务，读请求拆成 AR、R 两个通道任务。AW、W、AR 驱动线程各自从 mailbox 取请求并独立等待握手，B、R 响应线程各自等待返回并通过 `seq_item_port.put()` 把 response 交还给 sequence。

```text
write item
  -> AW mailbox -> AW channel thread -> AWVALID/AWADDR
  -> W  mailbox -> W  channel thread -> WVALID/WDATA/WSTRB
  -> B  mailbox -> B  response thread -> BRESP -> sequence response

read item
  -> AR mailbox -> AR channel thread -> ARVALID/ARADDR
  -> R  mailbox -> R  response thread -> RDATA/RRESP -> sequence response
```

这种 driver 结构和 AXI 通道模型一致：五个通道的驱动、等待和响应采集互不阻塞。`aw_delay` 和 `w_delay` 用来制造 AW 先到、W 先到、同时到和长延迟场景。DUT 的写接收逻辑要求 `AWVALID` 和 `WVALID` 同时有效后才拉起 `AWREADY/WREADY`，driver 因此必须在握手完成前保持 `VALID` 和 payload 稳定。

复位监听线程在 `ARESETN` 拉低期间持续清空 master 输出。复位释放后，driver 恢复到 idle 输出，再继续处理 reset 后的新事务。

## AXI monitor

`axi_monitor` 的责任是把 AXI interface 上已经完成的通道握手记录下来。它在每个 `posedge ACLK` 检查五个通道，哪个通道完成 `VALID && READY`，就创建一条 `axi_seq_item` 并广播。

| 通道 | 触发条件 | item 内容 |
|---|---|---|
| AW | `AWVALID && AWREADY` | `kind=AXI_CH_AW`，`addr=AWADDR` |
| W | `WVALID && WREADY` | `kind=AXI_CH_W`，`wdata=WDATA`，`wstrb=WSTRB` |
| B | `BVALID && BREADY` | `kind=AXI_CH_B`，`bresp=BRESP` |
| AR | `ARVALID && ARREADY` | `kind=AXI_CH_AR`，`addr=ARADDR` |
| R | `RVALID && RREADY` | `kind=AXI_CH_R`，`rdata=RDATA`，`rresp=RRESP` |

AXI 写事务的地址、数据、响应分布在 AW/W/B 三条通道上。monitor 先忠实记录每个通道事件，RM 再根据 AW、W、B 的顺序恢复完整写事务。这样 monitor 保持简单，事务级解释放在 RM 里。

## SPI monitor

`spi_monitor` 从 SPI pin 上识别一帧真实输出。它观察 `CS/SCLK/MOSI`，根据当前 SPI mode 选择采样边沿，把串行 bit 组装成 `spi_seq_item`。

SPI mode 决定 CPOL/CPHA，影响空闲电平和采样边沿；word length 决定这一帧有效 bit 数。monitor 必须按 DUT 当前模式解释 MOSI，否则 scoreboard 比较的数据会从采样阶段开始错位。

SPI monitor 输出的是 actual item：

```text
CS 拉低
  -> 根据 mode 等待采样边沿
  -> 按 word_len 收集 MOSI bit
  -> 形成 spi_seq_item
  -> spi_mtr_port.write(item)
```

## Reference model

`spi_ref_model` 根据 AXI 输入事务生成期望 SPI 输出。它接收 `axi_monitor` 发来的通道事件，恢复 AXI 写事务，并维护一份规格层面的寄存器 shadow。

当前 RM 关注三个地址：

| 地址 | 寄存器 | RM 行为 |
|---|---|---|
| `0x10` | `WORD_LEN` | `strb[0]` 有效时更新 `word_len_shadow` |
| `0x20` | `MOSI_DATA` | 按 `WSTRB` 更新 `mosi_data_shadow` 对应 byte |
| `0x00` | `START` | `strb[0] && data[0]` 时生成 expected SPI item |

RM 在 `START` 写 1 时才发出 expected item。这个规则对应 DUT 的工作方式：写 `MOSI_DATA` 只是更新待发送数据，写 `START` 才让 SPI master 使用当前配置和当前数据发帧。

```text
AXI monitor:
  AW(addr=0x20), W(data=0x12345678), B(OKAY)
RM:
  update mosi_data_shadow

AXI monitor:
  AW(addr=0x10), W(data=word_len), B(OKAY)
RM:
  update word_len_shadow

AXI monitor:
  AW(addr=0x00), W(data[0]=1), B(OKAY)
RM:
  create expected spi_seq_item
  expected.spi_data = mosi_data_shadow masked by word_len_shadow
  expected_spi_item.write(expected)
```

字长截断规则：

| `word_len_shadow` | 有效数据 |
|---:|---|
| `2'd0` | `mosi_data_shadow[31:0]` |
| `2'd1` | `mosi_data_shadow[15:0]` |
| `2'd2` | `mosi_data_shadow[7:0]` |
| `2'd3` | `mosi_data_shadow[3:0]` |

RM 还检查 AXI response。`BRESP/RRESP` 必须为 OKAY。出现 B 早于 AW/W、R 早于 AR 这类通道顺序错误时，RM 记录 protocol error 并在 report phase 报错。

reset 到来时，RM 清掉：

```text
axi_fifo
aw_addr_q / w_data_q / w_strb_q / ar_addr_q
word_len_shadow
mosi_data_shadow
```

这样 reset 后的 expected 只来自 reset 后重新发生的 AXI 事务。

## Scoreboard

`tb_scoreboard` 的责任是比较 expected SPI item 和 actual SPI item。expected 来自 RM，actual 来自 SPI monitor。SCB 当前只维护两个 FIFO 和比较计数，生成期望值和解释 AXI 配置的工作放在 RM 中。

当前 scoreboard 内部只有两个 FIFO：

| FIFO | 来源 | 内容 |
|---|---|---|
| `expected_spi_fifo` | `rm.expected_spi_item` | RM 产生的期望 SPI frame |
| `actual_spi_fifo` | `spi_mtr.spi_mtr_port` | SPI monitor 捕获的真实 SPI frame |

比较线程只处理 actual stream：

```systemverilog
forever begin
    actual_spi_fifo.get(actual);
    compare_spi_item(actual);
end
```

`compare_spi_item()` 先从 `expected_spi_fifo` 取一条 expected。expected FIFO 为空时收到 actual，说明 DUT 产生了额外 SPI 输出；expected 和 actual 数据不同，说明 DUT 输出数据与 AXI 输入事务推导出的结果不一致。

```text
actual arrives
  -> try_get expected
  -> expected empty: unexpected SPI
  -> data equal: match
  -> data different: mismatch
```

reset 到来时，SCB 同时 flush 两个 FIFO：

```systemverilog
expected_spi_fifo.flush();
actual_spi_fifo.flush();
```

这里用 `flush()` 是直接清空 `uvm_tlm_analysis_fifo` 的内部缓冲。reset 可能打断一帧 SPI，reset 前的 expected 和 reset 后的 actual 继续比较会产生假 mismatch。

## Coverage

`tb_coverage` 统计测试空间是否被打到。它接收 AXI monitor 和 SPI monitor 两路 transaction。AXI 侧更新当前配置 shadow，SPI 侧每出现一帧就采样一次 covergroup。

当前功能覆盖模型：

| Coverpoint / cross | 覆盖内容 |
|---|---|
| `cp_mode` | SPI mode 0/1/2/3 |
| `cp_wlen` | 32/16/8/4 bit |
| `cp_speed` | 四档 SCK 分频 |
| `cp_data` | zero / nonzero |
| `x_mode_wlen` | mode 与 word_len 组合 |
| `x_mode_speed` | mode 与 sck_speed 组合 |

覆盖率回答“场景有没有出现”。scoreboard 回答“DUT 输出是否正确”。这两个结论需要同时看：功能覆盖满说明测试空间已覆盖，scoreboard 无错误说明这些场景下 expected 和 actual 一致。

## SVA

SVA 检查的是 transaction 级 scoreboard 难以直接表达的周期级协议约束。AXI 侧重点覆盖 reset、握手等待和响应返回，SPI 侧覆盖 reset idle。SPI 片选和时钟时序由定向 test 做 sweep，并通过传输完成和 scoreboard 比较验证。

| 文件 | 检查内容 |
|---|---|
| `UVMTB/sva/axi_sva_checker.sv` | reset 期间 slave 输出 idle，reset 释放后无请求时保持 idle |
| `UVMTB/sva/axi_sva_checker.sv` | AW/W/AR/B/R 通道在 `VALID && !READY` 后保持 `VALID` 和 payload 稳定 |
| `UVMTB/sva/axi_sva_checker.sv` | 写请求接收后限定周期内返回 B 响应，读地址接收后限定周期内返回 R 响应 |
| `UVMTB/sva/spi_sva_checker.sv` | SPI 复位 idle |

`|=>` 表示从触发条件成立后的下一拍开始检查后件。`VALID && !READY |=> VALID && $stable(payload)` 的含义是：发送方已经声明 payload 有效但接收方还没有接收时，下一拍仍必须保持 `VALID` 和 payload 不变。条件没有触发的周期不做这条稳定性检查，因为协议只约束等待握手期间的 payload 保持行为。

## RAL 保留项

RAL 把 DUT 寄存器建模成 `uvm_reg` 对象，让 test 可以用 `reg.write()`、`reg.read()`、`peek()`、`poke()` 操作寄存器。

项目保留 RAL 文件用于寄存器模型冒烟检查：

| 文件 | 作用 |
|---|---|
| `UVMTB/ral/axi_spi_reg_block.sv` | 定义 10 个寄存器、字段、地址映射和 backdoor HDL path |
| `UVMTB/ral/axi_spi_reg_adapter.sv` | 在 `uvm_reg_bus_op` 和 `axi_seq_item` 之间转换 |
| `UVMTB/test/ral/ral_test.sv` | 做 frontdoor/backdoor 冒烟测试 |

`ral_test` 的核心流程：

```text
1. backdoor peek 检查复位值
2. WO 寄存器 frontdoor write，再 backdoor peek 确认物理寄存器写入
3. RO status frontdoor read，检查 idle busy=0
4. miso_data backdoor poke / frontdoor read 做路径演示
```

DUT 的多数配置寄存器通过 AXI 写入后可以影响 SPI master，但 frontdoor 读回并不返回这些配置值，所以 RAL 中按 WO 建模。验证这些寄存器写入是否成功时，用 frontdoor write 走真实 AXI 总线，再用 backdoor peek 读物理寄存器。简历主线聚焦 AXI-Lite 协议、SPI 功能/时序、RM/SCB 和 SVA，RAL 不作为核心卖点展开。

## 面试讲法

这个项目可以按链路讲。

```text
我验证的是 AXI4-Lite 到 SPI master 的桥接 IP。
AXI 侧通过寄存器配置 SPI mode、word length、SCK speed 和 MOSI data。
START 写 1 后，DUT 根据当前寄存器配置发起一帧 SPI 传输。

UVM 环境里 AXI agent 是 active，负责驱动 AXI-Lite 读写。
SPI monitor 是 passive，负责按 SPI mode 和 word length 采样真实 MOSI frame。
AXI monitor 把 AW/W/B/AR/R 通道事件发给 reference model。
reference model 根据 AXI 写事务维护配置 shadow，并在 START 写 1 时产生 expected SPI item。
scoreboard 接收 RM 的 expected item 和 SPI monitor 的 actual item，按 FIFO 顺序比较。
coverage 统计 mode、word length、speed、data 以及 cross。
SVA 覆盖 reset、payload stable until ready 和读写响应返回。
```

如果被问 reference model：

```text
这个项目的 RM 用 SystemVerilog 写在 UVM 环境里。
DUT 逻辑主要是寄存器配置到 SPI frame 的协议级转换，没有复杂算法，所以 SV transaction-level model 足够表达规格行为。
RM 从 AXI monitor 的事务出发，维护 word_len 和 mosi_data 的 shadow。
当 START 寄存器被写 1 时，RM 根据 shadow 生成期望 SPI 输出。
scoreboard 只比较 RM expected 和 SPI monitor actual。
```

如果被问 scoreboard：

```text
scoreboard 现在很简单。
它有 expected_spi_fifo 和 actual_spi_fifo。
expected 来自 reference model，actual 来自 SPI monitor。
actual 到来时取出最早的 expected 比较。
reset 时两个 FIFO 都 flush，避免 reset 前未完成的帧影响 reset 后比较。
```

## 剩余风险

- 代码覆盖没有收满，主要缺口在非法地址、部分响应位、地址低位和 SPI FSM 少量 transition。
- busy 期间重复 start 还可以作为负向场景补强。
- 当前 MISO 测试是定向模式，后续可以扩展到更多 mode/word_len 组合。
- 部分 test 仍使用固定时间等待，后续可以改成等待 CS、busy 或 monitor event。
